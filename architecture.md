# architecture.md — ТЗ проекта «Система управления задачами (Todo-лист)»

## 1. О чём проект (в двух словах)

Консольное приложение, где можно вести несколько списков задач: создавать задачи,
менять статус, ставить приоритет и дедлайн, искать и фильтровать.
Данные сохраняются в файл, чтобы после перезапуска ничего не терялось.

Пишем на ООП: **каждый класс отвечает за одну вещь**, ничего не сваливаем в одну кучу.

---

## 2. Главная идея: слои

Короче, представь пирамиду. Верхний слой умеет разговаривать с человеком,
нижний — с диском. Каждый знает только то, что под ним.

```
ConsoleUI        → общается с пользователем (ввод/вывод)
   ↓
TaskManager      → мозг приложения, вся бизнес-логика
   ↓
TaskList         → контейнер задач (один список/проект)
   ↓
Task             → одна конкретная задача

Storage          → отдельная ветка: сохранение/загрузка (знает только dict)
```

Правило зависимостей: **стрелки только вниз**.
`Task` не знает про `TaskManager`, `TaskList` не знает про `Storage`,
`Storage` не знает про классы вообще.

## 3. Классы, атрибуты, методы

### 3.0. Перечисления (Enum) — чтобы не писать строки руками

- **`TaskStatus`**: `NEW`, `IN_PROGRESS`, `DONE`, `CANCELED`
- **`Priority`**: `LOW`, `MEDIUM`, `HIGH`

Зачем: опечатка в строке `"done"` / `"Done"` — классический баг. Enum ловит это сразу.

---

### 3.1. `Task` — одна задача

Самый «тупой» и самый важный класс. Хранит данные и умеет менять только своё состояние.

**Атрибуты:**

| Атрибут | Тип | Смысл |
|---|---|---|
| `id` | `str` | UUID, генерится при создании, никогда не меняется |
| `title` | `str` | Название, обязательное, 1–120 символов |
| `description` | `str` | Подробности, по умолчанию `""` |
| `status` | `TaskStatus` | По умолчанию `NEW` |
| `priority` | `Priority` | По умолчанию `MEDIUM` |
| `created_at` | `datetime` | Ставится автоматически |
| `updated_at` | `datetime` | Обновляется при любом изменении |
| `deadline` | `datetime \| None` | Может отсутствовать |
| `completed_at` | `datetime \| None` | Заполняется при переходе в `DONE` |
| `tags` | `list[str]` | Метки: «работа», «суд», «учёба» |

**Методы:**

- `start()` — `NEW → IN_PROGRESS`
- `complete()` — в `DONE`, ставит `completed_at`
- `reopen()` — из `DONE/CANCELED` обратно в `NEW`, чистит `completed_at`
- `cancel()` — в `CANCELED`
- `update(**fields)` — меняет разрешённые поля + обновляет `updated_at`
- `set_deadline(dt)` — ставит/снимает дедлайн (в прошлом — ошибка)
- `is_overdue() -> bool` — дедлайн прошёл, а статус не `DONE/CANCELED`
- `add_tag(tag)` / `remove_tag(tag)`
- `to_dict() -> dict` / `from_dict(data) -> Task` (classmethod) — для сохранения
- `__str__()` — короткая строка для вывода

**Важно:** валидация своих полей живёт здесь.
Пустой `title` не создастся, даже если очень просят.

---

### 3.2. `TaskList` — список задач (проект)

Это «папка» с задачами. Умеет искать и считать,
но **не умеет сохранять и не знает про консоль**.

**Атрибуты:**

| Атрибут | Тип | Смысл |
|---|---|---|
| `id` | `str` | UUID списка |
| `name` | `str` | «Работа», «Учёба», уникально в рамках приложения |
| `description` | `str` | необязательно |
| `tasks` | `list[Task]` | приватный список, наружу только через методы |
| `created_at` | `datetime` | дата создания |

**Методы:**

- `add_task(task)` — добавить (проверяет, что `id` не дублируется)
- `remove_task(task_id)` — удалить, иначе `TaskNotFoundError`
- `get_task(task_id) -> Task` — найти одну
- `search(query) -> list[Task]` — по подстроке в `title`/`description`
- `filter(status=None, priority=None, tag=None) -> list[Task]` — комбинируемый фильтр
- `sort_by(key) -> list[Task]` — по дедлайну / приоритету / дате создания
- `get_overdue() -> list[Task]`
- `stats() -> dict` — всего, по статусам, % выполнения
- `to_dict()` / `from_dict()`
- `__len__()` — чтобы работал `len(task_list)`

**Важно:** `filter` и `sort_by` **возвращают новый список**, а не переставляют исходный.
Иначе сортировка «съедает» порядок пользователя.

---

### 3.3. `TaskManager` — мозг приложения

Единственный класс, который знают все верхние слои.
Любой сценарий («создай», «перенеси», «удали») — это его метод.

**Атрибуты:**

| Атрибут | Тип | Смысл |
|---|---|---|
| `lists` | `dict[str, TaskList]` | ключ — `id` списка |
| `storage` | `Storage` | подставляется снаружи (инъекция зависимости) |
| `active_list_id` | `str \| None` | список, с которым работаем сейчас |

**Методы:**

- `create_list(name, description="") -> TaskList`
- `delete_list(list_id)` / `rename_list(list_id, new_name)`
- `get_list(list_id) -> TaskList` / `get_all_lists()`
- `set_active_list(list_id)`
- `create_task(title, ...) -> Task` — создаёт `Task`, кладёт в активный список, сохраняет
- `edit_task(task_id, **fields)`
- `change_status(task_id, new_status)` — вызывает нужный метод задачи
- `delete_task(task_id)`
- `move_task(task_id, target_list_id)` — вынуть из одного списка, положить в другой
- `search_all(query) -> list[Task]` — поиск по всем спискам
- `get_overdue_all() -> list[Task]`
- `get_statistics() -> dict` — сводка по всем спискам
- `save()` — собирает `to_dict()` со всех списков → отдаёт в `storage`
- `load()` — берёт `dict` из `storage` → восстанавливает объекты

**Важно:** после любой изменяющей операции менеджер сам вызывает `save()`.
UI про сохранение не думает вообще.

### 3.4. `Storage` + реализации — работа с файлом

Абстрактный класс (интерфейс) и две реализации.
Смысл: завтра захочешь SQLite — меняешь один класс, остальной код не трогаешь.

**`Storage` (ABC):**
- `save(data: dict) -> None`
- `load() -> dict`

**`JsonFileStorage(Storage)`**
- Атрибуты: `file_path: str`, `encoding: str = "utf-8"`
- Методы: `save()`, `load()`, `_backup()` (копия файла перед перезаписью)
- Логика: файла нет → вернуть `{"lists": []}`;
  битый JSON → `StorageError`, но данные не затирать

**`InMemoryStorage(Storage)`**
- Атрибут: `_data: dict`
- Зачем: для тестов, чтобы не мусорить файлами

**Важно:** хранилище оперирует **только словарями**.
Никаких `Task` внутри — иначе слои склеятся.

### 3.5. `ConsoleUI` — общение с человеком

**Атрибуты:**

| Атрибут | Тип |
|---|---|
| `manager` | `TaskManager` |
| `commands` | `dict[str, callable]` — карта «команда → обработчик» |
| `running` | `bool` |

**Методы:**

- `run()` — главный цикл: показать меню → прочитать ввод → dispatch → повторить
- `show_menu()` / `show_lists()` / `show_tasks(tasks)` / `show_stats()`
- `ask_task_data() -> dict` — спрашивает поля у пользователя
- `handle_command(cmd, args)` — ищет обработчик в `commands`
- `show_error(message)` / `show_success(message)`

**Важно:** UI **не меняет объекты напрямую**.
Он только зовёт методы менеджера и красиво печатает результат.
Никакой бизнес-логики в `print`.

## 4. Как объекты взаимодействуют

### Кто кого знает

- `ConsoleUI` → знает `TaskManager` (и больше никого)
- `TaskManager` → знает `TaskList`, `Task`, `Storage`
- `TaskList` → знает только `Task`
- `Task` → знает только себя и Enum'ы
- `Storage` → не знает ни одного нашего класса

### Сценарий 1: запуск приложения

1. `main.py` создаёт `JsonFileStorage("data.json")`
2. Создаёт `TaskManager(storage)` → вызывает `manager.load()`
3. `Storage.load()` возвращает `dict` → менеджер через `TaskList.from_dict()`
   и `Task.from_dict()` собирает объекты
4. Создаёт `ConsoleUI(manager)` → `ui.run()`

### Сценарий 2: добавить задачу

```
Пользователь → UI: "add Купить молоко"
UI.ask_task_data() → собрал dict
UI → manager.create_task(title="Купить молоко", priority=HIGH)
    manager → Task(...)                    # объект сам валидирует поля
    manager → active_list.add_task(task)
    manager → storage.save(все списки в dict)
manager → вернул Task
UI.show_success("Задача #a1b2 создана")
```

### Сценарий 3: отметить выполненной

1. UI: `done a1b2` → `manager.change_status("a1b2", DONE)`
2. Менеджер находит список и задачу → `task.complete()`
3. Задача сама ставит `completed_at` и `updated_at`
4. Менеджер вызывает `save()`
5. UI печатает обновлённый список

### Сценарий 4: перенести задачу в другой список

`manager.move_task(task_id, target_id)` → `old_list.remove_task()` →
`new_list.add_task()` → `save()`.

Задача при этом **не меняется** — она не знает, в какой папке лежит.
Это и есть правильная зона ответственности.

### Сценарий 5: показать просроченные

UI → `manager.get_overdue_all()` → менеджер обходит списки →
каждый список спрашивает `task.is_overdue()` → результат собирается наверх →
UI печатает таблицу.

## 6. Бизнес-правила (инварианты)

1. `id` уникален и неизменяем; сравнение задач — по `id`, не по названию.
2. `title` не пустой и не длиннее 120 символов.
3. Дедлайн нельзя поставить в прошлом.
4. Переходы статусов: `NEW → IN_PROGRESS → DONE`; из `DONE` только `reopen()`;
   `CANCELED` — из любого незавершённого.
5. Имена списков уникальны; последний список удалить нельзя
   (или создаётся «Входящие» по умолчанию).
6. Любая мутация данных заканчивается сохранением.
7. Удаление списка удаляет его задачи (UI обязан спросить подтверждение).
8. Ошибки не роняют приложение: UI ловит `TodoError` и печатает понятный текст.

## 7. Порядок разработки

| Этап | Что делаем | Результат |
|---|---|---|
| 1 | `enums`, `Task`, `exceptions` | задача создаётся и меняет статус в тестах |
| 2 | `TaskList` | добавление, поиск, фильтр, статистика |
| 3 | `Storage` + `InMemoryStorage` | сериализация туда-обратно без потерь |
| 4 | `TaskManager` | все сценарии работают без консоли |
| 5 | `JsonFileStorage` | данные переживают перезапуск |
| 6 | `ConsoleUI` + `main.py` | рабочее приложение (MVP) |
| 7 | Тесты, рефакторинг | стабильность |

Правило: **сначала логика, потом интерфейс**.
Пока менеджер работает в тестах — консоль подключается за полчаса.

## 8. Что можно докрутить потом

- `User` + права доступа (списки общие/личные)
- `RecurringTask(Task)` — наследование: повторяющиеся задачи
- `Notifier` + паттерн Observer — напоминания о дедлайнах
- `Command` + история → отмена действия (`undo`)
- `SqliteStorage(Storage)` — проверка, что абстракция хранилища действительно рабочая
- GUI или веб-API поверх того же `TaskManager` — без переписывания логики
